# Power Trade Lab · 评估体系与回归测试规范

> 本文档记录系统四大模块的评估框架设计、基线数据、测试经验，以及后续改动的回归测试规范。
> **核心原则：一切质量判断基于数据，不靠感觉。任何关键改动必须跑回归对比。**

---

## 一、评估架构总览

每个关键模块采用统一模式：

```
测试集(golden cases) → 运行器 → 指标计算 → 基线对比 → 发现回归
```

四大模块：

| 模块 | 评估文件 | 测试维度 | 指标 |
|------|---------|---------|------|
| RAG检索 | `app/ai/eval/` | 20题标准问答集(5类型×3难度) | Recall@K, MRR, Precision@K |
| 交易撮合 | `app/trade/eval_matching.py` | 9个边界case(价格/量/方向) | 通过率, 结算一致性, 公平性 |
| 考试系统 | `app/exam/eval_exam.py` | 组卷/判分/蓝图/去重/难度 | 通过率 |
| 知识库 | `app/knowledge/eval_kb.py` | 索引完整性/分块质量/去重/分类/维度 | 通过率 |

统一入口：`app/eval/regression.py` 的 `run_all_evals(db)`
API：`GET /api/eval/all`（需管理员权限）

## 三、RAG检索评估经验

### 测试集设计
- 20题，覆盖5种查询类型：
  - `policy_number`(文号精确)：143号文、SD003标准
  - `province`(省份特定)：浙江/山东/安徽/福建
  - `semantic`(语义近似)：电价怎么计算、储能参与市场
  - `exact`(精确匹配)：华北区域电力市场运营规则
  - `broad`(宽泛概念)：什么是节点边际电价

### 关键发现（数据支撑）

**三模式对比（top_k=5）**：
| 模式 | Recall | MRR | Precision |
|------|--------|-----|-----------|
| dense | 0.90 | 0.767 | 0.24 |
| sparse | 0.85 | 0.775 | 0.278 |
| **hybrid** | **0.95** | **0.796** | 0.26 |

**分维度最优模式**：
- policy_number → sparse最优（BM25对文号/代号精确匹配更强）
- semantic → dense最优（向量对语义理解更强）
- 总体 → hybrid最优（融合两者优势）

**top_k调优**：
| top_k | Recall | Precision | 适用场景 |
|-------|--------|-----------|---------|
| 3 | 0.85 | 0.367 | 精确搜索（找特定文档）|
| **5** | **0.95** | **0.26** | **默认推荐** |
| 10 | 1.0 | 0.16 | AI问答（宁多召回）|

### 最佳配置建议
- 默认：hybrid + top_k=5
- AI问答：hybrid + top_k=10
- 文号搜索：sparse模式

## 四、测试经验总结

### 1. 分块质量直接影响检索效果
- **发现**：首次评估发现6个<20字的噪声块 + 1个844字的超长块
- **根因**：`chunk_text` 逗号不切（导致超长）+ 无最小长度过滤（导致噪声）
- **修复**：增加逗号分割、超长句硬切、`<20字`过滤
- **验证**：重建索引后超短块=0，MRR从0.796→0.808

### 2. LLM调用模式必须区分场景
- **发现**：`_call_openai` 无条件加 `response_format=json_object`，导致RAG问答（需自然语言）失败
- **修复**：拆分 `json_mode` 参数，生题用JSON，问答用自然语言
- **教训**：LLM调用层必须根据调用方需求区分输出格式

### 3. 测试期望必须符合业务逻辑
- **发现**：交易评估"极大量买单"case期望全额成交，但10万MW远超市场流动性
- **修复**：修正为"部分成交"（这才是正确的业务行为）
- **教训**：测试case的期望值要基于真实业务逻辑，不是"理想情况"

### 4. 同文档去重影响Recall评估
- 当前每篇文档只返回1个片段（同doc取最高分块）
- 这对"长文档多段相关"场景是信息损失
- 评估Recall时要注意这个特性

## 五、回归测试规范

### 什么时候跑回归
1. **修改检索逻辑**（embedding/bm25/RRF）→ 必须跑RAG评估
2. **修改撮合引擎**（matching.py）→ 必须跑交易评估
3. **修改考试逻辑**（engine.py/router.py）→ 必须跑考试评估
4. **修改知识库入库**（ingest/embedding）→ 必须跑知识库评估
5. **任何涉及多模块的改动** → 跑 `/api/eval/all` 全量回归

### 怎么跑
```bash
# 方式1：API（需管理员token）
curl -H "Authorization: Bearer <token>" http://localhost:8000/api/eval/all

# 方式2：Python直接调用
cd backend && source venv/bin/activate
python -c "
from app.db.database import SessionLocal
from app.eval.regression import run_all_evals
db = SessionLocal()
report = run_all_evals(db)
print(f'总体: {report[\"overall_score\"]}')
for k, m in report['modules'].items():
    print(f'  {m[\"name\"]}: {m.get(\"pass_rate\")}')
"
```

### 回归判定标准
- **通过**：pass_rate ≥ 基线值（见第二节）
- **回归**：pass_rate < 基线值 → 必须定位原因并修复
- **提升**：pass_rate > 基线值 → 更新基线，记录经验

### 发现回归后怎么办
1. 定位失败的case（看details里的具体失败项）
2. 分析是"测试期望不合理"还是"代码逻辑错误"
3. 修复后重跑回归确认
4. 更新本文档的基线数据
